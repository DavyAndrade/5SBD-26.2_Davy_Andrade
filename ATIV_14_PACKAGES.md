# 5SBD — Packages no Oracle Database

Um **package** é uma estrutura de encapsulamento que agrupa logicamente tipos de dados, variáveis, constantes, cursores, exceções, procedures e funções relacionados em uma única unidade modular compilada no catálogo do banco de dados.

---

## 1. Fundamentos Teóricos

### Divisão arquitetural

Um package é dividido em duas partes independentes:

| Parte | O que é | Para que serve |
|---|---|---|
| **Specification** (especificação) | Interface pública (`CREATE OR REPLACE PACKAGE nome AS ...`) | Declara os itens visíveis externamente. A aplicação ou usuário com privilégio `EXECUTE` acessa apenas o que está aqui. |
| **Body** (corpo) | Implementação privada (`CREATE OR REPLACE PACKAGE BODY nome AS ...`) | Contém o código executável dos subprogramas, além de variáveis, tipos e subprogramas auxiliares estritamente privados (invisíveis fora do pacote). |

### Vantagens de engenharia

- **Encapsulamento e ocultação de informação (information hiding):** protege a lógica interna. É possível alterar a implementação no Body sem quebrar os programas consumidores nem invalidar objetos dependentes.
- **Modularidade e coesão:** agrupa operações de um mesmo domínio de negócio (ex: `pkg_gestao_pedidos`, `pkg_folha_pagamento`).
- **Desempenho e carregamento em memória:** na primeira chamada a qualquer elemento do pacote, o Oracle carrega o pacote inteiro para a Shared Pool, acelerando todas as invocações subsequentes sem novos acessos a disco.
- **Sobrecarga de subprogramas (overloading):** permite declarar múltiplos procedimentos ou funções com o mesmo nome na especificação, desde que suas listas de parâmetros diferem em número, ordem ou família de tipos de dados.
- **Persistência de estado e variáveis globais de sessão:** variáveis declaradas na especificação ou no corpo mantêm seus valores durante todo o ciclo de vida da sessão conectada.
- **Bloco de inicialização:** código executado automaticamente uma única vez quando o pacote é carregado na sessão (bloco `BEGIN ... END nome;` no final do corpo).

## 2. Roteiro Prático: Laboratório no Oracle APEX

### Etapa 1: Esquema base

```sql
CREATE TABLE tb_prod_estoque (
    id_produto   NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    descricao    VARCHAR2(100) NOT NULL,
    preco        NUMBER(10,2) NOT NULL,
    qtd_estoque  NUMBER(6) NOT NULL
);

CREATE TABLE tb_registro_vendas (
    id_venda       NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    id_produto     NUMBER REFERENCES tb_prod_estoque(id_produto),
    qtd_vendida    NUMBER(6) NOT NULL,
    valor_venda    NUMBER(12,2) NOT NULL,
    data_venda     DATE DEFAULT SYSDATE NOT NULL
);

INSERT INTO tb_prod_estoque (descricao, preco, qtd_estoque) VALUES ('Notebook Dell Vostro', 4500.00, 15);
INSERT INTO tb_prod_estoque (descricao, preco, qtd_estoque) VALUES ('Monitor UltraWide LG 29', 1250.00, 30);
INSERT INTO tb_prod_estoque (descricao, preco, qtd_estoque) VALUES ('Mouse Sem Fio Logitech', 120.00, 50);
COMMIT;
```

### Etapa 2: Especificação do pacote

```sql
CREATE OR REPLACE PACKAGE pkg_gestao_vendas AS
    -- Constantes globais públicas
    c_taxa_desconto_padrao CONSTANT NUMBER := 0.05; -- 5% de desconto padrão

    -- Exceção customizada pública
    e_estoque_insuficiente EXCEPTION;

    -- Procedimento sobrecarregado (Versão 1: venda padrão pelo ID do produto)
    PROCEDURE realizar_venda(
        p_id_produto   IN  NUMBER,
        p_quantidade   IN  NUMBER,
        p_valor_final  OUT NUMBER
    );

    -- Procedimento sobrecarregado (Versão 2: venda com aplicação de cupom/desconto manual)
    PROCEDURE realizar_venda(
        p_id_produto   IN  NUMBER,
        p_quantidade   IN  NUMBER,
        p_desconto_pct IN  NUMBER,
        p_valor_final  OUT NUMBER
    );

    -- Função pública de consulta de disponibilidade
    FUNCTION verificar_disponibilidade(
        p_id_produto IN NUMBER,
        p_quantidade IN NUMBER
    ) RETURN BOOLEAN;

    -- Função pública para obter o total faturado no dia
    FUNCTION faturamento_diario RETURN NUMBER;
END pkg_gestao_vendas;
/
```

### Etapa 3: Corpo do pacote

```sql
CREATE OR REPLACE PACKAGE BODY pkg_gestao_vendas AS
    -- Variável privada de sessão para contabilizar operações realizadas
    g_total_vendas_sessao NUMBER := 0;

    -- Subprograma PRIVADO (visível apenas dentro do corpo deste pacote)
    PROCEDURE registrar_baixa_estoque(
        p_id_produto IN NUMBER,
        p_quantidade IN NUMBER
    ) IS
    BEGIN
        UPDATE tb_prod_estoque
        SET qtd_estoque = qtd_estoque - p_quantidade
        WHERE id_produto = p_id_produto;
    END registrar_baixa_estoque;

    -- Implementação da função pública verificar_disponibilidade
    FUNCTION verificar_disponibilidade(
        p_id_produto IN NUMBER,
        p_quantidade IN NUMBER
    ) RETURN BOOLEAN IS
        v_estoque_atual NUMBER := 0;
    BEGIN
        SELECT qtd_estoque INTO v_estoque_atual
        FROM tb_prod_estoque
        WHERE id_produto = p_id_produto;

        RETURN (v_estoque_atual >= p_quantidade);
    EXCEPTION
        WHEN NO_DATA_FOUND THEN
            RETURN FALSE;
    END verificar_disponibilidade;

    -- Implementação da Procedure sobrecarregada (Versão 1: venda sem desconto manual)
    PROCEDURE realizar_venda(
        p_id_produto   IN  NUMBER,
        p_quantidade   IN  NUMBER,
        p_valor_final  OUT NUMBER
    ) IS
    BEGIN
        -- Delega para a versão completa aplicando desconto zero
        realizar_venda(p_id_produto, p_quantidade, 0, p_valor_final);
    END realizar_venda;

    -- Implementação da Procedure sobrecarregada (Versão 2: venda completa)
    PROCEDURE realizar_venda(
        p_id_produto   IN  NUMBER,
        p_quantidade   IN  NUMBER,
        p_desconto_pct IN  NUMBER,
        p_valor_final  OUT NUMBER
    ) IS
        v_preco_unitario NUMBER(10,2);
        v_total_bruto    NUMBER(12,2);
    BEGIN
        -- 1. Validar disponibilidade chamando a função do pacote
        IF NOT verificar_disponibilidade(p_id_produto, p_quantidade) THEN
            RAISE e_estoque_insuficiente;
        END IF;

        -- 2. Obter preço atual do produto
        SELECT preco INTO v_preco_unitario
        FROM tb_prod_estoque
        WHERE id_produto = p_id_produto;

        -- 3. Calcular valores
        v_total_bruto := v_preco_unitario * p_quantidade;
        p_valor_final := v_total_bruto - (v_total_bruto * NVL(p_desconto_pct, 0));

        -- 4. Chamar subprograma privado para debitar estoque
        registrar_baixa_estoque(p_id_produto, p_quantidade);

        -- 5. Registrar movimentação na tabela de vendas
        INSERT INTO tb_registro_vendas (id_produto, qtd_vendida, valor_venda)
        VALUES (p_id_produto, p_quantidade, p_valor_final);

        -- 6. Incrementar contador da sessão
        g_total_vendas_sessao := g_total_vendas_sessao + 1;

        COMMIT;
    EXCEPTION
        WHEN e_estoque_insuficiente THEN
            ROLLBACK;
            RAISE_APPLICATION_ERROR(-20010, 'Estoque insuficiente para atender à quantidade solicitada.');
        WHEN OTHERS THEN
            ROLLBACK;
            RAISE_APPLICATION_ERROR(-20099, 'Erro ao processar venda no pacote: ' || SQLERRM);
    END realizar_venda;

    -- Implementação da função faturamento_diario
    FUNCTION faturamento_diario RETURN NUMBER IS
        v_faturamento NUMBER(12,2) := 0;
    BEGIN
        SELECT NVL(SUM(valor_venda), 0) INTO v_faturamento
        FROM tb_registro_vendas
        WHERE TRUNC(data_venda) = TRUNC(SYSDATE);

        RETURN v_faturamento;
    END faturamento_diario;

    -- Bloco de Inicialização do Pacote (executa 1 vez por sessão quando carregado)
    BEGIN
        g_total_vendas_sessao := 0;
    END pkg_gestao_vendas;
/
```

### Etapa 4: Testes dos métodos sobrecarregados e tratamento de erros

```sql
SET SERVEROUTPUT ON

-- Teste 1: Executando a Versão 1 da procedure (sem desconto manual)
DECLARE
    v_total NUMBER;
BEGIN
    pkg_gestao_vendas.realizar_venda(
        p_id_produto  => 1,
        p_quantidade  => 2,
        p_valor_final => v_total
    );
    DBMS_OUTPUT.PUT_LINE('Venda 1 Concluída! Total a Pagar: R$ ' || TO_CHAR(v_total, 'FM999G999D00'));
END;
/

-- Teste 2: Executando a Versão 2 da procedure (com 10% de desconto)
DECLARE
    v_total NUMBER;
BEGIN
    pkg_gestao_vendas.realizar_venda(
        p_id_produto   => 2,
        p_quantidade   => 4,
        p_desconto_pct => 0.10,
        p_valor_final  => v_total
    );
    DBMS_OUTPUT.PUT_LINE('Venda 2 (com cupom) Concluída! Total: R$ ' || TO_CHAR(v_total, 'FM999G999D00'));
END;
/

-- Teste 3: Consulta do faturamento diário consolidado através da função do pacote
SELECT pkg_gestao_vendas.faturamento_diario AS faturamento_hoje FROM DUAL;

-- Teste 4: Tentativa de venda excedendo o estoque (disparo da exceção customizada)
DECLARE
    v_total NUMBER;
BEGIN
    pkg_gestao_vendas.realizar_venda(
        p_id_produto  => 1,
        p_quantidade  => 500, -- Quantidade muito superior ao estoque
        p_valor_final => v_total
    );
END;
/
```

Com a carga inicial, o teste 1 (2 × Notebook = R$ 9.000,00) e o teste 2 (4 × Monitor = R$ 5.000,00 com desconto 10% = R$ 4.500,00) executam com sucesso. O teste 4 falha com `ORA-20010: Estoque insuficiente para atender à quantidade solicitada.` e faz `ROLLBACK`.

### Etapa 5: Demonstração de encapsulamento privado

```sql
SET SERVEROUTPUT ON

BEGIN
    pkg_gestao_vendas.registrar_baixa_estoque(1, 5);
END;
/
```

Resultado: `PLS-00302: component 'REGISTRAR_BAIXA_ESTOQUE' must be declared`. A procedure existe apenas no `BODY`, é privada, e não pode ser invocada externamente.

SELECT object_name, object_type, status, last_ddl_time

ORDER BY object_type;

SELECT line, text
FROM user_source

SELECT line, text
FROM user_source
WHERE name = 'PKG_GESTAO_VENDAS' AND type = 'PACKAGE BODY'

A especificação mostra status `VALID` após a criação do corpo. Alterar apenas o corpo recompila só o corpo, sem invalidar objetos que dependem da especificação.

## 3. Exercícios Práticos de Fixação

### Exercício 1: Procedure de reposição de estoque

Adicione à especificação e ao corpo de `pkg_gestao_vendas` uma procedure pública chamada `repor_estoque`.

```sql
-- Especificação
PROCEDURE repor_estoque(p_id_produto IN NUMBER, p_quantidade IN NUMBER);
```

```sql
-- Corpo
PROCEDURE repor_estoque(p_id_produto IN NUMBER, p_quantidade IN NUMBER) IS
    e_quantidade_invalida EXCEPTION;
BEGIN
    IF p_quantidade <= 0 THEN
        RAISE e_quantidade_invalida;
    END IF;

    UPDATE tb_prod_estoque
       SET qtd_estoque = qtd_estoque + p_quantidade
     WHERE id_produto = p_id_produto;

    IF SQL%ROWCOUNT = 0 THEN
        RAISE_APPLICATION_ERROR(-20011, 'Produto não encontrado.');
    END IF;

    COMMIT;
EXCEPTION
    WHEN e_quantidade_invalida THEN
        ROLLBACK;
        RAISE_APPLICATION_ERROR(-20012, 'Quantidade de reposição deve ser positiva.');
    WHEN OTHERS THEN
        ROLLBACK;
        RAISE_APPLICATION_ERROR(-20099, 'Erro ao reposicionar estoque: ' || SQLERRM);
END repor_estoque;
```

### Exercício 2: Dependências e invalidação

**Pergunta:** Se você modificar a lógica interna de um procedimento dentro do `PACKAGE BODY` e recompilá-lo, os programas externos que chamam a especificação ficam inválidos? E se alterar a assinatura de um procedimento na `PACKAGE SPECIFICATION`?

**Resposta:**

- **Modificação apenas no Body:** **Não.** Programas externos continuam válidos. A especificação (contrato público) não mudou, então objetos que dependem dela não são invalidados. Apenas o pacote é recompilado.
- **Alteração da assinatura na Specification:** **Sim.** O contrato público mudou. Qualquer objeto que referencie o subprograma alterado (procedures externas, functions, outros packages, blocos anônimos compilados) é marcado como `INVALID` e precisa ser recompilado antes de voltar a funcionar. Isso ocorre porque o Oracle registra dependências de objetos no dicionário de dados (`USER_DEPENDENCIES`), e a especificação é o alvo dessas dependências.

### Exercício 3: Variáveis globais de sessão

Adicione à especificação e ao corpo:

```sql
-- Especificação
FUNCTION obter_total_vendas_sessao RETURN NUMBER;

-- Corpo
FUNCTION obter_total_vendas_sessao RETURN NUMBER IS
BEGIN
    RETURN g_total_vendas_sessao;
END obter_total_vendas_sessao;
```

Ao abrir **duas abas/sessões diferentes** no APEX e executar `obter_total_vendas_sessao` em cada uma, cada sessão verá o **seu próprio** valor de `g_total_vendas_sessao`. O estado de pacote é **por sessão**, não compartilhado globalmente entre sessões distintas. Isso ocorre porque o estado do pacote vive na memória da sessão (UGA/SGA da sessão), e não em uma tabela ou estrutura de banco compartilhada.

## 4. Checklist de Boas Práticas e Arquitetura Corporativa

| Prática | Recomendação |
|---|---|
| **Especificação enxuta** | Declare apenas o que for estritamente necessário para os consumidores externos. Mantenha tudo o mais privado no corpo. |
| **Sobrecarga consciente** | Evite sobrecargas com parâmetros que possam gerar ambiguidade de conversão implícita (ex: um com `NUMBER` e outro com `VARCHAR2`). |
| **Independência de compilação** | Corrija erros no corpo do pacote sem recompilar a especificação, para não derrubar dependências de produção. |
| **Padrão de nomenclatura** | Adote convenções corporativas claras (ex: `pkg_<modulo>_<dominio>`). |
