# 5SBD — Stored Procedures no Oracle Database

Uma **stored procedure** é um bloco PL/SQL nomeado, compilado e guardado no dicionário de dados do Oracle. Ela encapsula uma sequência de comandos procedurais e DML/TCL, e é chamada pelo nome a partir da aplicação ou de outro bloco PL/SQL.

---

## 1. Fundamentos Teóricos

### Por que usar

- **Desempenho e rede**: uma chamada substitui dezenas de round-trips entre aplicação e banco. Toda a lógica roda no servidor.
- **Centralização da regra**: a regra de negócio mora em um lugar só. Mudou a regra, muda a procedure — todos os consumidores (Java, Python, APEX) passam a usar a versão nova sem alteração de código.
- **Segurança**: dá para conceder apenas `EXECUTE` na procedure, sem dar `SELECT`/`INSERT`/`UPDATE`/`DELETE` direto nas tabelas. O `AUTHID DEFINER` executa com privilégio do dono; `AUTHID CURRENT_USER` executa com privilégio de quem chamou.
- **Compilação e cache**: o código fica pré-compilado (p-code) na Shared Pool / Library Cache, reaproveitado por todas as sessões.

### Anatomia

1. **Cabeçalho**: nome, `CREATE OR REPLACE` e lista de parâmetros.
2. **Seção declarativa**: entre o cabeçalho e o `BEGIN`, para variáveis, constantes, cursores e exceções nomeadas. **Não** usa a palavra `DECLARE` (isso é só em bloco anônimo).
3. **Seção executável**: `BEGIN ... END`.
4. **Seção de exceções**: `EXCEPTION`, tratando erros de execução.

### Modos de parâmetro

| Modo | Direção | Comportamento |
|---|---|---|
| `IN` | entrada | Padrão. Somente leitura dentro do bloco; não pode receber atribuição. |
| `OUT` | saída | O valor de entrada é ignorado; a procedure atribui e devolve o valor. |
| `IN OUT` | bidirecional | Recebe valor, pode ler e alterar, devolve o valor modificado. |

### Procedure vs Function

| Critério | Procedure | Function |
|---|---|---|
| Objetivo | Executar ações e controle transacional | Calcular e retornar um valor |
| Retorno | Sem `RETURN` obrigatório; devolve via `OUT`/`IN OUT` | Exige `RETURN` no cabeçalho e no corpo |
| Uso em SQL | Não pode ser chamada em `SELECT`/`WHERE` | Pode ser chamada em SQL, respeitando as regras de pureza |

## 2. Roteiro Prático: Laboratório no Oracle APEX

### Etapa 1: Esquema base

```sql
CREATE TABLE tb_contas (
    id_conta     NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    titular      VARCHAR2(100) NOT NULL,
    saldo        NUMBER(12,2) DEFAULT 0 NOT NULL,
    status       VARCHAR2(10) DEFAULT 'ATIVA' CHECK (status IN ('ATIVA', 'BLOQUEADA'))
);

CREATE TABLE tb_movimentacoes (
    id_movimento    NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    id_conta_origem NUMBER REFERENCES tb_contas(id_conta),
    id_conta_dest   NUMBER REFERENCES tb_contas(id_conta),
    tipo_operacao   VARCHAR2(20) NOT NULL,
    valor           NUMBER(12,2) NOT NULL,
    data_movimento  DATE DEFAULT SYSDATE NOT NULL
);

INSERT INTO tb_contas (titular, saldo, status) VALUES ('Alexandre Louzada', 5000.00, 'ATIVA');
INSERT INTO tb_contas (titular, saldo, status) VALUES ('Empresa Tech Solutions', 12000.00, 'ATIVA');
INSERT INTO tb_contas (titular, saldo, status) VALUES ('Conta Bloqueada Teste', 1500.00, 'BLOQUEADA');
COMMIT;
```

### Etapa 2: Procedure de depósito com parâmetros `IN` e `OUT`

```sql
CREATE OR REPLACE PROCEDURE prc_realizar_deposito (
    p_id_conta    IN  NUMBER,
    p_valor       IN  NUMBER,
    p_novo_saldo  OUT NUMBER,
    p_status_msg  OUT VARCHAR2
) IS
    v_status_conta VARCHAR2(10);
BEGIN
    IF p_valor <= 0 THEN
        p_status_msg := 'ERRO: O valor do depósito deve ser maior que zero.';
        p_novo_saldo := NULL;
        RETURN;
    END IF;

    SELECT status, saldo INTO v_status_conta, p_novo_saldo
    FROM tb_contas
    WHERE id_conta = p_id_conta;

    IF v_status_conta <> 'ATIVA' THEN
        p_status_msg := 'ERRO: A conta está bloqueada ou inativa.';
        p_novo_saldo := NULL;
        RETURN;
    END IF;

    UPDATE tb_contas
       SET saldo = saldo + p_valor
     WHERE id_conta = p_id_conta
    RETURNING saldo INTO p_novo_saldo;

    INSERT INTO tb_movimentacoes (id_conta_dest, tipo_operacao, valor)
    VALUES (p_id_conta, 'DEPOSITO', p_valor);

    COMMIT;
    p_status_msg := 'SUCESSO: Depósito efetuado com êxito.';

EXCEPTION
    WHEN NO_DATA_FOUND THEN
        p_status_msg := 'ERRO: Conta inexistente.';
        p_novo_saldo := NULL;
        ROLLBACK;
    WHEN OTHERS THEN
        p_status_msg := 'ERRO INESPERADO: ' || SQLERRM;
        p_novo_saldo := NULL;
        ROLLBACK;
END prc_realizar_deposito;
/
```

### Etapa 3: Execução com bloco anônimo

Procedure com parâmetro `OUT` não é chamada direto no SQL; usa-se um bloco PL/SQL.

```sql
SET SERVEROUTPUT ON

DECLARE
    v_saldo_atual NUMBER;
    v_mensagem    VARCHAR2(200);
BEGIN
    prc_realizar_deposito(
        p_id_conta   => 1,
        p_valor      => 1500.00,
        p_novo_saldo => v_saldo_atual,
        p_status_msg => v_mensagem
    );

    DBMS_OUTPUT.PUT_LINE('Resultado: ' || v_mensagem);
    DBMS_OUTPUT.PUT_LINE('Novo Saldo: R$ ' || TO_CHAR(v_saldo_atual, 'FM999G999D00'));
END;
/
```

Saída esperada: `SUCESSO` e saldo `6.500,00` (5.000 + 1.500).

### Etapa 4: Procedure transacional completa (transferência)

```sql
CREATE OR REPLACE PROCEDURE prc_transferir_fundos (
    p_origem  IN NUMBER,
    p_destino IN NUMBER,
    p_valor   IN NUMBER
) IS
    v_saldo_origem NUMBER;
    v_status_orig  VARCHAR2(10);
    v_status_dest  VARCHAR2(10);
    e_saldo_insuficiente EXCEPTION;
    e_conta_bloqueada    EXCEPTION;
BEGIN
    IF p_valor <= 0 THEN
        RAISE_APPLICATION_ERROR(-20001, 'Valor de transferência inválido.');
    END IF;

    SELECT saldo, status INTO v_saldo_origem, v_status_orig
    FROM tb_contas
    WHERE id_conta = p_origem
    FOR UPDATE;

    IF v_status_orig <> 'ATIVA' THEN
        RAISE e_conta_bloqueada;
    END IF;

    IF v_saldo_origem < p_valor THEN
        RAISE e_saldo_insuficiente;
    END IF;

    SELECT status INTO v_status_dest
    FROM tb_contas
    WHERE id_conta = p_destino;

    IF v_status_dest <> 'ATIVA' THEN
        RAISE e_conta_bloqueada;
    END IF;

    UPDATE tb_contas SET saldo = saldo - p_valor WHERE id_conta = p_origem;
    UPDATE tb_contas SET saldo = saldo + p_valor WHERE id_conta = p_destino;

    INSERT INTO tb_movimentacoes (id_conta_origem, id_conta_dest, tipo_operacao, valor)
    VALUES (p_origem, p_destino, 'TRANSFERENCIA', p_valor);

    COMMIT;
    DBMS_OUTPUT.PUT_LINE('Transferência de R$ ' || p_valor || ' concluída com sucesso.');

EXCEPTION
    WHEN e_saldo_insuficiente THEN
        ROLLBACK;
        RAISE_APPLICATION_ERROR(-20002, 'Falha: Saldo insuficiente na conta de origem.');
    WHEN e_conta_bloqueada THEN
        ROLLBACK;
        RAISE_APPLICATION_ERROR(-20003, 'Falha: Uma das contas envolvidas está bloqueada.');
    WHEN NO_DATA_FOUND THEN
        ROLLBACK;
        RAISE_APPLICATION_ERROR(-20004, 'Falha: Conta de origem ou destino não localizada.');
    WHEN OTHERS THEN
        ROLLBACK;
        RAISE_APPLICATION_ERROR(-20099, 'Erro inesperado na transferência: ' || SQLERRM);
END prc_transferir_fundos;
/
```

Detalhe de execução: o `RAISE_APPLICATION_ERROR(-20001)` do valor inválido acontece dentro da seção executável, então cai no `WHEN OTHERS` e sai como `-20099` com a mensagem original dentro. Se quiser código próprio para esse caso, basta capturar `-20001` antes do `OTHERS`.

### Etapa 5: Testes

```sql
-- válida: 1.000 da conta 2 para a conta 1
BEGIN
    prc_transferir_fundos(p_origem => 2, p_destino => 1, p_valor => 1000.00);

-- saldo insuficiente

    prc_transferir_fundos(p_origem => 1, p_destino => 2, p_valor => 99999.00);

BEGIN
    prc_transferir_fundos(p_origem => 1, p_destino => 3, p_valor => 100.00);
```

Estado final esperado depois de depósito de 1.500 na conta 1, transferência válida de 1.000 (2→1) e as duas falhas:

- conta 2: R$ 11.000,00

- movimentações: 1 depósito de 1.500 e 1 transferência de 1.000

## 3. Exercícios Práticos de Fixação

### Exercício 1: Reajuste em massa

```sql
CREATE OR REPLACE PROCEDURE prc_reajustar_saldo_em_massa (
    p_percentual       IN  NUMBER,
    p_total_atualizado OUT NUMBER
) IS
BEGIN
    IF p_percentual <= 0 THEN
        RAISE_APPLICATION_ERROR(-20010, 'O percentual de reajuste deve ser maior que zero.');
    END IF;

    UPDATE tb_contas
       SET saldo = saldo * (1 + p_percentual / 100)
     WHERE status = 'ATIVA';

    p_total_atualizado := SQL%ROWCOUNT;
    COMMIT;
EXCEPTION
    WHEN OTHERS THEN
        ROLLBACK;
        p_total_atualizado := 0;
        RAISE;
END prc_reajustar_saldo_em_massa;
/
```

`SQL%ROWCOUNT` logo depois do `UPDATE` devolve quantas linhas foram reajustadas — é exatamente o que o parâmetro de saída precisa. Só contas `'ATIVA'` entram no `WHERE`; a bloqueada fica de fora.

Teste:

```sql
SET SERVEROUTPUT ON
DECLARE
    v_qtd NUMBER;
BEGIN
    prc_reajustar_saldo_em_massa(p_percentual => 10, p_total_atualizado => v_qtd);
    DBMS_OUTPUT.PUT_LINE('Contas reajustadas: ' || v_qtd);
END;
/
```

### Exercício 2: Por que o `FOR UPDATE`

O `SELECT ... FOR UPDATE` bloqueia as linhas lidas até o `COMMIT` ou `ROLLBACK`. Na transferência, isso impede que duas sessões leiam o mesmo saldo ao mesmo tempo e decidam, as duas, que há dinheiro suficiente.

Sem o `FOR UPDATE`, o cenário clássico de **lost update** acontece: a sessão A lê saldo 1.000, a sessão B lê o mesmo 1.000, A debita 800 e comita, B (que validou contra o valor velho) debita mais 800 e comita. Resultado: saldo -600 e uma transferência que nunca deveria ter passado. Com dezenas de transações simultâneas o problema escala: saldo negativo, transferências duplicadas, extrato inconsistente. O `FOR UPDATE` serializa o acesso àquelas linhas e mantém a validação e a atualização dentro da mesma janela consistente.

### Exercício 3: Parâmetro `IN OUT`

```sql
CREATE OR REPLACE PROCEDURE prc_sanitizar_texto (
    p_texto IN OUT VARCHAR2
) IS
BEGIN
    p_texto := UPPER(TRIM(p_texto));
END prc_sanitizar_texto;
/

SET SERVEROUTPUT ON
DECLARE
    v_nome VARCHAR2(100) := '   banco de dados oracle   ';
BEGIN
    prc_sanitizar_texto(v_nome);
    DBMS_OUTPUT.PUT_LINE('[' || v_nome || ']');
END;
/
```

Saída: `[BANCO DE DADOS ORACLE]` — sem espaços nas pontas e tudo em maiúsculo.

## 4. Checklist de Boas Práticas

- **Tratamento de exceções rigoroso**: capture o erro e faça `ROLLBACK` para não deixar transação aberta segurando lock.
- **Controle de concorrência**: use `SELECT ... FOR UPDATE` quando for ler para depois alterar.
- **Responsabilidade única**: uma procedure, um objetivo. Procedure monolítica é difícil de testar e de manter.
- **Modularização via packages**: agrupe procedures e funções relacionadas em packages (spec + body) — melhora organização de namespace, permite membros privados e facilita o carregamento em memória.
