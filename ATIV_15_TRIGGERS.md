# 5SBD — Triggers no Oracle Database

Um **trigger** (gatilho) é um bloco PL/SQL nomeado associado a uma tabela, view ou evento do sistema, executado de forma automática e implícita sempre que um evento especificado ocorre (DML, DDL ou eventos de banco/sessão).

---

## 1. Fundamentos Teóricos

### Classificação e níveis de disparo

| Timing | Quando dispara | Ideal para |
|---|---|---|
| **BEFORE** | Antes da operação DML ser aplicada fisicamente | Validações, higienização, derivação de valores, regras impeditivas. |
| **AFTER** | Após a operação DML ter sido aplicada | Auditoria, replicação, geração de logs históricos. |
| **INSTEAD OF** | Sobre views complexas não atualizáveis | Interceptar comandos DML e redirecionar para as tabelas base. |

| Nível de execução | Comportamento |
|---|---|
| **Statement-Level** (padrão) | Dispara uma única vez para o comando SQL como um todo, independentemente de quantas linhas foram afetadas (inclusive zero). |
| **Row-Level** (`FOR EACH ROW`) | Dispara individualmente para cada linha inserida, alterada ou excluída. |

### Pseudoregistros :NEW e :OLD

| Operação DML | :OLD | :NEW |
|---|---|---|
| **INSERT** | NULL | Contém os novos valores inseridos |
| **UPDATE** | Contém os dados **antes** da alteração | Contém os **novos** dados propostos |
| **DELETE** | Contém os dados **removidos** | NULL |

### Predicados condicionais (para uso no corpo)

| Predicado | Retorna TRUE se… |
|---|---|
| **INSERTING** | o evento for uma instrução INSERT |
| **UPDATING** | o evento for uma instrução UPDATE |
| **DELETING** | o evento for uma instrução DELETE |

### A cláusula WHEN

Permite condicionar a execução em nível de linha **antes** de iniciar o contexto PL/SQL, economizando recursos:

```sql
CREATE TRIGGER tg_empio
BEFORE INSERT ON tb_empregados
FOR EACH ROW
WHEN (NEW.salario > 10000)  -- avaliação mais rápida
BEGIN
   -- corpo do trigger
END;
```

### O fenômeno da tabela mutante (ORA-04091)

**Causa:** Um trigger **ROW-Level** tenta `SELECT` ou `DML` na própria tabela que está sendo processada durante a transação. O Oracle bloqueia essa operação para evitar inconsistências.

**Soluções de arquitetura:**
- **Compound Triggers** (Oracle 11g+): junta a seção BEFORE STATEMENT, BEFORE ROW, AFTER ROW e AFTER STATEMENT no mesmo objeto, usando variáveis locais que persistem entre as chamadas.
- **Variáveis de sessão em pacotes:** grava o dado em um pacote no BEFORE STATEMENT, lê no AFTER ROW.
- **Mover lógica para aplicação:** o trigger apenas sinaliza; a validação real acontece no código cliente.

## 2. Roteiro Prático: Laboratório no Oracle APEX

### Etapa 1: Esquema base

```sql
CREATE TABLE tb_empregados (
    id_empregado   NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nome           VARCHAR2(100) NOT NULL,
    cargo          VARCHAR2(50) NOT NULL,
    salario        NUMBER(10,2) NOT NULL,
    status         VARCHAR2(20) DEFAULT 'ATIVO' NOT NULL,
    data_criacao   DATE DEFAULT SYSDATE
);

CREATE TABLE tb_auditoria_salarios (
    id_audit         NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    id_empregado     NUMBER NOT NULL,
    operacao         VARCHAR2(10) NOT NULL,
    salario_anterior NUMBER(10,2),
    salario_novo     NUMBER(10,2),
    usuario_db       VARCHAR2(50) DEFAULT USER,
    data_evento      TIMESTAMP DEFAULT SYSTIMESTAMP
);

INSERT INTO tb_empregados (nome, cargo, salario) VALUES ('Ana Beatriz Costa', 'ANALISTA PL', 5200.00);
INSERT INTO tb_empregados (nome, cargo, salario) VALUES ('Lucas Albuquerque', 'DESENVOLVEDOR SR', 9800.00);
INSERT INTO tb_empregados (nome, cargo, salario) VALUES ('Mariana Silveira', 'COORDENADORA TI', 12500.00);
COMMIT;
```

### Etapa 2: Trigger BEFORE Row-Level (validação e higienização)

```sql
CREATE OR REPLACE TRIGGER trg_empregados_biu_valida
BEFORE INSERT OR UPDATE ON tb_empregados
FOR EACH ROW
BEGIN
    :NEW.nome  := UPPER(TRIM(:NEW.nome));
    :NEW.cargo := UPPER(TRIM(:NEW.cargo));

    IF :NEW.salario < 1412.00 THEN
        RAISE_APPLICATION_ERROR(-20001, 'Violação: salário inferior ao piso.');
    END IF;

    IF UPDATING THEN
        IF :NEW.salario < :OLD.salario THEN
            RAISE_APPLICATION_ERROR(-20002, 'Violação: redução nominal de salário não permitida.');
        END IF;
    END IF;
END trg_empregados_biu_valida;
/
```

### Etapa 3: Trigger AFTER Row-Level (auditoria histórica)

```sql
CREATE OR REPLACE TRIGGER trg_empregados_auditoria
AFTER INSERT OR UPDATE OR DELETE ON tb_empregados
FOR EACH ROW
BEGIN
    IF INSERTING THEN
        INSERT INTO tb_auditoria_salarios (id_empregado, operacao, salario_anterior, salario_novo)
        VALUES (:NEW.id_empregado, 'INSERT', NULL, :NEW.salario);
    ELSIF UPDATING THEN
        IF :NEW.salario <> :OLD.salario THEN
            INSERT INTO tb_auditoria_salarios (id_empregado, operacao, salario_anterior, salario_novo)
            VALUES (:OLD.id_empregado, 'UPDATE', :OLD.salario, :NEW.salario);
        END IF;
    ELSIF DELETING THEN
        INSERT INTO tb_auditoria_salarios (id_empregado, operacao, salario_anterior, salario_novo)
        VALUES (:OLD.id_empregado, 'DELETE', :OLD.salario, NULL);
    END IF;
END trg_empregados_auditoria;
/
```

### Etapa 4: Trigger BEFORE Statement-Level (controle de janela)

```sql
CREATE OR REPLACE TRIGGER trg_bloqueio_fim_semana
BEFORE DELETE ON tb_empregados
DECLARE
    v_dia_semana VARCHAR2(20);
BEGIN
    v_dia_semana := TO_CHAR(SYSDATE, 'DY', 'NLS_DATE_LANGUAGE=ENGLISH');

    IF v_dia_semana IN ('SAT', 'SUN') THEN
        RAISE_APPLICATION_ERROR(-20005, 'Exclusão de dados proibida durante finais de semana.');
    END IF;
END trg_bloqueio_fim_semana;
/
```

### Etapa 5: Testes práticos

```sql
-- Teste 1: inserção com higienização automática
INSERT INTO tb_empregados (nome, cargo, salario) VALUES ('fernando rocha', 'analista de suporte', 3500.00);
COMMIT;

-- Verificar padronização em maiúsculas
SELECT id_empregado, nome, cargo, salario FROM tb_empregados WHERE nome LIKE '%ROCHA%';

-- Teste 2: tentativa de redução salarial (deve falhar)
UPDATE tb_empregados SET salario = 3000.00 WHERE nome LIKE '%ROCHA%';

-- Teste 3: aumento salarial legítimo
UPDATE tb_empregados SET salario = 4200.00 WHERE nome LIKE '%ROCHA%';
COMMIT;

-- Teste 4: consulta da trilha de auditoria
SELECT id_audit, id_empregado, operacao, salario_anterior, salario_novo, usuario_db, data_evento
FROM tb_auditoria_salarios
ORDER BY id_audit;
```

```sql
SELECT trigger_name, trigger_type, triggering_event, table_name, status
FROM user_triggers
WHERE table_name = 'TB_EMPREGADOS'
ORDER BY trigger_name;

ALTER TRIGGER trg_empregados_biu_valida DISABLE;
```

## 3. Exercícios Práticos de Fixação

### Exercício 1: Trigger INSTEAD OF

Criar uma view complexa com JOIN ou agregação e construir uma trigger `INSTEAD OF INSERT` que intercepte a inserção na view e direcione as colunas para as tabelas subjacentes correspondentes.

### Exercício 2: Simulação de tabela mutante (ORA-04091)

Criar um trigger `AFTER INSERT OR UPDATE ON tb_empregados FOR EACH ROW` que tente executar `SELECT COUNT(*) FROM tb_empregados WHERE cargo = :NEW.cargo`. Tentar fazer uma alteração de dados e observar o erro `ORA-04091: table is mutating`. Explicar por que o Oracle impede essa leitura concorrente.

### Exercício 3: Cláusula WHEN

Modificar o trigger de auditoria salarial usando a cláusula `WHEN (NEW.salario <> OLD.salario)` na própria definição do cabeçalho do trigger, explicando a economia de processamento em relação a fazer a checagem com `IF` dentro do corpo PL/SQL.

## 4. Checklist de Boas Práticas

- **Uso criterioso**: triggers executam de forma transparente e implícita; excesso dificulta a depuração de sistemas transacionais complexos.
- **Não confundir com regras declarativas**: sempre prefira restrições declarativas (`NOT NULL`, `CHECK`, `UNIQUE`, `FOREIGN KEY`) antes de recorrer a triggers para validações simples.
- **Atenção ao ORA-04091**: nunca faça consultas à tabela que acionou o gatilho dentro de um trigger **ROW-Level**.
- **Tratamento de exceções**: se um trigger lançar exceção não tratada, toda a instrução DML chamadora é imediatamente abortada e revertida.
