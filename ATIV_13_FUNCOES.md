# 5SBD — Stored Functions no Oracle Database

Uma **stored function** é um bloco PL/SQL nomeado, compilado e guardado no catálogo do banco. A diferença estrutural em relação à procedure é uma só, mas define tudo: a função **obrigatoriamente retorna um valor** via `RETURN`, e por isso pode ser chamada dentro de SQL (`SELECT`, `WHERE`, `ORDER BY`).

---

## 1. Fundamentos Teóricos

### Para que serve

- Transformar e padronizar dados dentro de consultas.
- Cálculos matemáticos, financeiros e estatísticos reutilizáveis.
- Regras de negócio determinísticas.
- Enriquecer relatórios analíticos (colunas calculadas).

### Anatomia

1. **Cabeçalho**: nome, parâmetros e o tipo de retorno.
2. **Seção declarativa**: entre o `IS`/`AS` e o `BEGIN`. Variáveis, constantes, cursores. Sem `DECLARE`.
3. **Seção executável**: `BEGIN ... END`, com pelo menos um `RETURN` alcançável em todos os caminhos.
4. **Seção de exceções**: opcional, mas recomendável — em função chamada por SQL, exceção não tratada derruba a consulta inteira.

### Níveis de pureza (por que função em SQL tem regra)

Para rodar dentro de SQL, a função precisa respeitar:

- **Sem DML**: não pode executar `INSERT`/`UPDATE`/`DELETE` nas tabelas envolvidas na consulta nem alterar estado global do banco.
- **Sem controle de transação**: nada de `COMMIT`/`ROLLBACK`/`SAVEPOINT`, salvo contexto isolado com `PRAGMA AUTONOMOUS_TRANSACTION`.
- **Sem alterar estado de pacote** em execução remota ou paralela.

Violar isso dá `ORA-14551: cannot perform a DML operation inside a query` (o exercício 2 mostra na prática).

### Cláusulas de otimização

| Cláusula | O que faz |
|---|---|
| **DETERMINISTIC** | Diz ao otimizador que a mesma entrada sempre gera a mesma saída. Pré-requisito para **Function-Based Index** e para otimização em consultas e materialized views. |
| **RESULT_CACHE** | Guarda os resultados na SGA. Chamada com os mesmos argumentos volta da memória, sem executar o corpo de novo. |

### Function vs Procedure

| Característica | Function | Procedure |
|---|---|---|
| Retorno | Obrigatório (`RETURN`) | Opcional (sem tipo de retorno no cabeçalho) |
| Chamada em SQL | Sim (`SELECT`, `WHERE`, etc.) | Não |
| Propósito | Computar e retornar valor | Executar fluxo, DML e controle transacional |
| Parâmetros | Predominantemente `IN` | Usa `IN`, `OUT` e `IN OUT` |
| Chamada em PL/SQL | Lado direito de atribuição (`v := fnc(...)`) | Instrução autônoma (`proc(...);`) |

### Etapa 2: Função determinística (IRRF)

```sql
CREATE OR REPLACE FUNCTION fnc_calcular_irrf (
    p_salario_bruto IN NUMBER
) RETURN NUMBER
DETERMINISTIC
IS
    v_imposto NUMBER(10,2) := 0;
BEGIN
    IF p_salario_bruto IS NULL OR p_salario_bruto <= 2259.20 THEN
        v_imposto := 0;
    ELSIF p_salario_bruto <= 2826.65 THEN
        v_imposto := (p_salario_bruto * 0.075) - 169.44;
    ELSIF p_salario_bruto <= 3751.05 THEN
        v_imposto := (p_salario_bruto * 0.15) - 381.44;
    ELSIF p_salario_bruto <= 4664.68 THEN
        v_imposto := (p_salario_bruto * 0.225) - 662.77;
    ELSE
        v_imposto := (p_salario_bruto * 0.275) - 896.00;
    END IF;

    RETURN ROUND(GREATEST(v_imposto, 0), 2);
EXCEPTION
    WHEN OTHERS THEN
        RETURN 0;
END fnc_calcular_irrf;
/
```

O `DETERMINISTIC` aqui é legítimo: o resultado depende só do parâmetro. Se a função usasse `SYSDATE` ou consultasse tabela, o `DETERMINISTIC` seria uma mentira para o otimizador.

### Etapa 3: Função com consulta ao banco (comissão)

```sql
CREATE OR REPLACE FUNCTION fnc_obter_comissao (
    p_id_colaborador IN NUMBER,
    p_mes_ano        IN VARCHAR2
) RETURN NUMBER IS
    v_total_vendas NUMBER(12,2) := 0;
    v_percentual   NUMBER(5,4)  := 0;
BEGIN
    SELECT NVL(SUM(total_vendido), 0)
      INTO v_total_vendas
      FROM tb_vendas_colaborador
     WHERE id_colaborador = p_id_colaborador
       AND mes_ano = p_mes_ano;

    IF v_total_vendas >= 100000.00 THEN
        v_percentual := 0.05;
    ELSIF v_total_vendas >= 50000.00 THEN
        v_percentual := 0.035;
    ELSIF v_total_vendas > 0 THEN
        v_percentual := 0.02;
    ELSE
        v_percentual := 0;
    END IF;

    RETURN ROUND(v_total_vendas * v_percentual, 2);
EXCEPTION
    WHEN NO_DATA_FOUND THEN
        RETURN 0;
    WHEN OTHERS THEN
        RETURN 0;
END fnc_obter_comissao;
/
```

Essa função **não** é `DETERMINISTIC` — o resultado depende do estado da tabela. Chamar isso em `SELECT` de volume alto é o cenário clássico do problema N+1.

### Etapa 4: Funções em consultas analíticas

```sql
SELECT c.id_colaborador,
       c.nome,
       c.departamento,
       c.salario_base,
       fnc_obter_comissao(c.id_colaborador, '10/2026') AS comissao_outubro,
       (c.salario_base + fnc_obter_comissao(c.id_colaborador, '10/2026')) AS remuneracao_bruta,
       fnc_calcular_irrf(c.salario_base + fnc_obter_comissao(c.id_colaborador, '10/2026')) AS desconto_irrf,
       (c.salario_base + fnc_obter_comissao(c.id_colaborador, '10/2026'))
       - fnc_calcular_irrf(c.salario_base + fnc_obter_comissao(c.id_colaborador, '10/2026')) AS salario_liquido_estimado
FROM tb_colaboradores c
ORDER BY remuneracao_bruta DESC;

SELECT nome, salario_base
FROM tb_colaboradores
WHERE fnc_calcular_irrf(salario_base) > 300.00;
```

```sql

```

## 3. Exercícios Práticos de Fixação

### Exercício 1: Tempo de casa em anos

```sql
CREATE OR REPLACE FUNCTION fnc_calcular_tempo_casa (
    p_data_admissao IN DATE
) RETURN NUMBER IS
    v_anos NUMBER;
BEGIN
    IF p_data_admissao IS NULL THEN
        RETURN NULL;
    END IF;

    v_anos := FLOOR(MONTHS_BETWEEN(SYSDATE, p_data_admissao) / 12);
    RETURN GREATEST(v_anos, 0);
EXCEPTION
    WHEN OTHERS THEN
        RETURN NULL;
END fnc_calcular_tempo_casa;
/
```

Teste:

```sql
SELECT nome, data_admissao, fnc_calcular_tempo_casa(data_admissao) AS anos_de_casa
FROM tb_colaboradores
ORDER BY anos_de_casa DESC;
```

`MONTHS_BETWEEN` devolve a diferença em meses (com fração); dividir por 12 e aplicar `FLOOR` corta os meses que ainda não completaram mais um ano. O `GREATEST(...,0)` protege contra data futura.

### Exercício 2: Violação de pureza (ORA-14551)

```sql
CREATE OR REPLACE FUNCTION fnc_teste_dml RETURN NUMBER IS
BEGIN
    UPDATE tb_colaboradores
       SET salario_base = salario_base
     WHERE id_colaborador = 1;

    RETURN 1;
END fnc_teste_dml;
/

SELECT fnc_teste_dml() FROM dual;
```

Retorno: `ORA-14551: cannot perform a DML operation inside a query`.

Motivo: quando a função é chamada de dentro de uma consulta, ela roda dentro do snapshot de leitura consistente daquele `SELECT`. Executar DML ali quebraria a garantia de que a consulta vê um estado único dos dados (e poderia gerar efeitos colaterais por linha). Se a função precisa mesmo de DML isolado, o caminho é `PRAGMA AUTONOMOUS_TRANSACTION` — com a consciência de que o dado gravado não será desfeito pelo `ROLLBACK` da transação chamadora.

### Exercício 3: Function-Based Index

```sql
CREATE INDEX idx_colab_irrf ON tb_colaboradores (fnc_calcular_irrf(salario_base));
```

Antes do índice, `WHERE fnc_calcular_irrf(salario_base) > 300` gera `TABLE ACCESS FULL` — o Oracle precisa calcular a função linha a linha. Depois do índice, o plano passa a `INDEX RANGE SCAN` em `IDX_COLAB_IRRF`, porque o valor calculado já está armazenado na estrutura do índice.

Observação prática: a tabela do laboratório tem 4 linhas, então o CBO pode continuar preferindo full scan mesmo com o índice (custo de ler o índice + tabela não compensa em volume minúsculo). Para ver a mudança de plano de forma clara, gere estatísticas (`DBMS_STATS.GATHER_TABLE_STATS`) e teste com mais linhas. E lembre: FBI só funciona se a função for `DETERMINISTIC` — se a query escrever a expressão de outra forma, o índice é ignorado.

## 4. Checklist de Boas Práticas

- **Garantia de retorno**: todo caminho lógico (todos os `IF`/`ELSE` e todos os `EXCEPTION`) precisa chegar a um `RETURN`.
- **Problema N+1**: evitar `SELECT` dentro de função chamada linha a linha em volume grande. Prefira `JOIN`/subquery no SQL principal.
- **Determinismo honesto**: só declare `DETERMINISTIC` em função pura, sem `SYSDATE` e sem consultar tabela.
- **Encapsulamento em packages**: em produção, agrupe funções correlatas em packages em vez de deixar funções soltas; melhora organização e carregamento em memória.
