# 5SBD — Unidade 5: Materialized Views

Nessa unidade a gente vê o oposto da View padrão. A View padrão é só a query guardada no banco — nada em disco, e toda vez que você chama ela refaz tudo. A **Materialized View (MView)** roda a query de verdade e **guarda o resultado em disco**, como se fosse uma tabela com o resumo já calculado. Consulta pesada passa a ser leitura de tabela.

## Para que serve

- Painéis e relatórios de BI que não aguentam rodar SUM em cima de milhões de linhas toda vez.
- Consolidar volume transacional em resumo (por dia, categoria, região).
- Ler dados replicados de outro banco (DBLINK) localmente, sem puxar rede a cada consulta.
- Acelerar consulta analítica pesada em ambiente OLTP sem sobrecarregar o processamento.

## Como o dado é atualizado (Refresh)

Método (o *como*):

- **COMPLETE** — refaz tudo do zero.
- **FAST** — só aplica o que mudou desde o último refresh, usando o log `MLOG$`.
- **FORCE** — o padrão: tenta FAST, se não der, cai no COMPLETE.
- **NEVER** — não atualiza mais.

Modo temporal (o *quando*):

- **ON DEMAND** — você dispara na mão ou agendando (Scheduler) com `DBMS_MVIEW.REFRESH`.
- **ON COMMIT** — atualiza sozinho a cada `COMMIT` na tabela base.

Cuidado com `ON COMMIT`: o refresh acontece dentro da transação do usuário, o `COMMIT` fica mais lento e pode segurar lock. Em OLTP de alta concorrência, não use.

## Query Rewrite

É o otimizador (CBO) que troca a sua consulta nas tabelas base pela MView, sem você alterar o SQL. Para funcionar precisa `ENABLE QUERY REWRITE` na criação e a permissão `GLOBAL_QUERY_REWRITE` para o usuário. A troca é transparente para a aplicação.

### 2. Materialized View Log (obrigatório para FAST)

Sem esse log não existe refresh incremental. É ele que registra o que mudou na `tb_vendas`.

```sql
CREATE MATERIALIZED VIEW LOG ON tb_vendas
WITH ROWID, SEQUENCE (id_produto, quantidade, valor_total)
INCLUDING NEW VALUES;
```

### 3. A Materialized View

```sql
CREATE MATERIALIZED VIEW mv_vendas_por_produto
BUILD IMMEDIATE
REFRESH FAST ON DEMAND
ENABLE QUERY REWRITE
AS
SELECT v.id_produto,
       COUNT(*)            AS total_transacoes,
       SUM(v.quantidade)   AS qtd_total_vendida,
       SUM(v.valor_total)  AS faturamento_total,
       COUNT(v.valor_total) AS count_faturamento
FROM tb_vendas v
GROUP BY v.id_produto;
```

Por que tem `COUNT(*)` e `COUNT(valor_total)` junto do `SUM`? O Oracle usa esses contadores para ajustar as somas quando você apaga ou altera linha — é o que permite o FAST funcionar em agregação.

### 4. Conferência inicial

```sql
SELECT p.nome_produto, p.categoria, mv.total_transacoes,
       mv.qtd_total_vendida, mv.faturamento_total
FROM mv_vendas_por_produto mv
JOIN tb_produtos p ON p.id_produto = mv.id_produto
ORDER BY mv.faturamento_total DESC;
```

### 5. Novos dados e refresh

```sql
INSERT INTO tb_vendas (id_produto, quantidade, data_venda, valor_total)
VALUES (1, 5, SYSDATE, 22500.00);

-- antes do refresh: a MV ainda está com o valor antigo (é física, não virtual)
SELECT * FROM mv_vendas_por_produto WHERE id_produto = 1;

BEGIN
    DBMS_MVIEW.REFRESH(LIST => 'MV_VENDAS_POR_PRODUTO', METHOD => 'F');
END;
/

-- depois do refresh: valor atualizado
SELECT * FROM mv_vendas_por_produto WHERE id_produto = 1;
```

## Exercícios

1. **`mv_vendas_categoria`** — faturamento e quantidade de vendas **por categoria**, o que exige join entre `tb_vendas` e `tb_produtos`. Configure com `REFRESH COMPLETE ON DEMAND`. Complete aqui porque join não costuma ser elegível para FAST (mudança em duas tabelas exigiria log nas duas).
2. **`ON COMMIT`** — crie uma MView nesse modo e insira dados com `COMMIT`. Repare que o commit fica mais lento: o refresh roda dentro da sua transação. Conclusão: só em ambiente controlado.
3. **Dicionário de dados** — para ver o que existe no seu schema:

```sql
SELECT owner, mview_name, refresh_mode, refresh_method, last_refresh_date
FROM user_mviews;

SELECT master, log_table, log_trigger
FROM user_mview_logs;
```

## Boas práticas (resumo)

- FAST para tabela grande com pontualidade de alterações; COMPLETE para tabela pequena ou regra de agregação que o FAST não aceita.
- Longe de `ON COMMIT` em OLTP de alta concorrência.
- A MView é física, então vale indexar as colunas usadas em `WHERE`/`ORDER BY` dos relatórios.
- Fique de olho no `MLOG$`: se a MView fica muito tempo sem refresh, o log cresce sem parar e come espaço da tablespace.
