# 5SBD — Synonyms no Oracle Database

Um **synonym** é um alias para qualquer objeto de um schema Oracle — tabela, view, materialized view, sequence, procedure, function, package, type ou até outro synonym. Não guarda dado nem estrutura: é só uma entrada lógica no dicionário de dados apontando para o objeto real.

---

## 1. Fundamentos Teóricos

### Definição e propósito

O synonym existe para você escrever `clientes` em vez de `erp_financeiro.tb_clientes_faturamento_v2`. O ponteiro fica no dicionário; o objeto continua onde sempre esteve.

### Vantagens arquiteturais

- **Transparência de localização e schema**: a aplicação não precisa conhecer o schema dono nem o nome físico completo.
- **Isolamento e segurança indireta**: esconde o nome real, o padrão de nomenclatura e o proprietário — reduz a exposição da estrutura interna para ferramentas e usuários finais.
- **Manutenção e refatoração**: se a tabela for renomeada, particionada, trocada por view ou movida de schema, basta re-apontar o synonym. Nenhum SQL da aplicação muda.
- **Abstração de objetos remotos**: `SELECT * FROM produtos` em vez de `SELECT * FROM tb_produtos@db_link_matriz`.

### Classificação

| Tipo | Pertencimento | Visibilidade | Permissão exigida |
|---|---|---|---|
| **Private Synonym** | Schema de quem criou | Só o dono do schema (ou quem recebeu privilégio) | `CREATE SYNONYM` |
| **Public Synonym** | Schema especial `PUBLIC` | Todos os usuários do banco | `CREATE PUBLIC SYNONYM` |

### Ordem de resolução de nomes

Quando você referencia um objeto sem qualificar (`SELECT * FROM funcionarios`), o Oracle resolve nesta ordem:

1. Objeto local do próprio schema do usuário conectado.
2. Sinônimo privado do schema do usuário.
3. Sinônimo público (`PUBLIC`).
4. Nada encontrado: erro `ORA-00942: table or view does not exist`.

### Synonym não é privilégio

Ponto que mais cai em prova: o synonym é só conveniência de endereçamento. Ele **não concede acesso**. Quem consulta via synonym continua precisando do privilégio de objeto (`SELECT`, `INSERT`, `UPDATE`, `EXECUTE` etc.) concedido pelo dono do objeto base ou pela role. Sem grant, o synonym não ajuda em nada — dá `ORA-00942` ou `ORA-01031` na cara.

## 2. Roteiro Prático: Laboratório no Oracle APEX

### Etapa 1: Tabela com nomenclatura técnica complexa

```sql
CREATE TABLE tb_cad_clientes_corp_nacional (
    id_cliente      NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    codigo_empresa  VARCHAR2(15) NOT NULL,
    razao_social    VARCHAR2(100) NOT NULL,
    cidade          VARCHAR2(50) NOT NULL,
    limite_credito  NUMBER(12,2) NOT NULL,
    status_conta    VARCHAR2(15) DEFAULT 'ATIVO' NOT NULL
);

INSERT INTO tb_cad_clientes_corp_nacional (codigo_empresa, razao_social, cidade, limite_credito, status_conta)
VALUES ('CORP-001', 'Logística Integrada Sudeste SA', 'Rio de Janeiro', 250000.00, 'ATIVO');

INSERT INTO tb_cad_clientes_corp_nacional (codigo_empresa, razao_social, cidade, limite_credito, status_conta)
VALUES ('CORP-002', 'Rede Varejista do Brasil Ltda', 'São Paulo', 500000.00, 'ATIVO');

INSERT INTO tb_cad_clientes_corp_nacional (codigo_empresa, razao_social, cidade, limite_credito, status_conta)
VALUES ('CORP-003', 'Metalúrgica Vale do Paraíba', 'Belo Horizonte', 180000.00, 'INATIVO');

COMMIT;
```

### Etapa 2: Sinônimo privado (abstração semântica)

```sql
CREATE OR REPLACE SYNONYM clientes
FOR tb_cad_clientes_corp_nacional;

SELECT id_cliente, codigo_empresa, razao_social, cidade, limite_credito
FROM clientes
WHERE status_conta = 'ATIVO';
```

A consulta fica legível e o código da aplicação deixa de depender do nome físico gigante.

### Etapa 3: DML transparente via synonym

```sql
INSERT INTO clientes (codigo_empresa, razao_social, cidade, limite_credito, status_conta)
VALUES ('CORP-004', 'Distribuidora Farmacêutica Rio', 'Niterói', 320000.00, 'ATIVO');
COMMIT;

UPDATE clientes
SET limite_credito = limite_credito * 1.10
WHERE codigo_empresa = 'CORP-004';
COMMIT;

SELECT codigo_empresa, razao_social, limite_credito FROM clientes WHERE codigo_empresa = 'CORP-004';
SELECT codigo_empresa, razao_social, limite_credito FROM tb_cad_clientes_corp_nacional WHERE codigo_empresa = 'CORP-004';
```

As duas últimas consultas devolvem a mesma linha: o synonym é só o apontador, o dado está na tabela base.

### Etapa 4: Abstração de sequences

```sql
CREATE SEQUENCE seq_tb_cad_clientes_corp_id
    START WITH 500
    INCREMENT BY 1
    NOCACHE;

CREATE OR REPLACE SYNONYM seq_clientes
FOR seq_tb_cad_clientes_corp_id;

SELECT seq_clientes.NEXTVAL AS proximo_id FROM DUAL;
SELECT seq_clientes.CURRVAL AS id_atual FROM DUAL;
```

### Etapa 5: Refatoração transparente (troca por view)

```sql
CREATE OR REPLACE VIEW vw_clientes_ativos AS
SELECT id_cliente, codigo_empresa, razao_social, cidade, limite_credito
FROM tb_cad_clientes_corp_nacional
WHERE status_conta = 'ATIVO';

-- re-aponta o synonym para a view
CREATE OR REPLACE SYNONYM clientes
FOR vw_clientes_ativos;

-- a aplicação continua executando exatamente a mesma consulta
SELECT * FROM clientes;
```

Nenhuma linha de SQL da aplicação mudou. O `CREATE OR REPLACE SYNONYM` só trocou o alvo no dicionário — agora os dados vêm filtrados pela view.

### Etapa 6: Auditoria no dicionário de dados

```sql
SELECT synonym_name, table_owner, table_name, db_link
FROM user_synonyms
ORDER BY synonym_name;

-- remoção segura: apaga só o apontador, o objeto alvo continua vivo
-- DROP SYNONYM clientes;
```

## 3. Exercícios Práticos de Fixação

### Exercício 1: Ambiente multi-schema e privilégios

**Cenário**: fazer `ANALISTA_BI` consultar `HR.EMPLOYEES` usando só `SELECT * FROM func;`.

**Resolução**: são dois passos distintos — privilégio e apontamento.

```sql
-- 1. o dono do objeto concede leitura (isto é o que dá acesso)
GRANT SELECT ON hr.employees TO analista_bi;

-- 2. o usuário cria o atalho no próprio schema
CREATE SYNONYM func FOR hr.employees;

-- 3. agora funciona
SELECT * FROM func;
```

Sem o `GRANT`, o synonym existe mas a consulta falha. Grant e synonym são coisas separadas.

### Exercício 2: Ordem de resolução de nomes

**Cenário**: o usuário tem uma tabela `PEDIDOS`, um synonym privado `PEDIDOS` (para `FATURAMENTO.TB_PEDIDOS`) e um synonym público `PEDIDOS` (para `GLOBAL.TB_PEDIDOS`). O que `SELECT * FROM pedidos;` retorna?

**Resolução**: retorna a **tabela física do próprio schema**. A ordem de resolução é objeto local (1), synonym privado (2), synonym público (3). O objeto local ganha sempre.

### Exercício 3: Sinônimos órfãos

**Cenário**: o que acontece com o synonym se a tabela base sofrer `DROP TABLE`?

**Resolução**: o synonym **não** é removido automaticamente. Ele fica no dicionário apontando para o nada — sinônimo órfão/inválido. Na hora de consultar, o Oracle tenta resolver o alvo, não encontra e devolve `ORA-00942: table or view does not exist`. A limpeza é manual (`DROP SYNONYM`) ou via rotina de auditoria.

---

## 4. Checklist de Boas Práticas e Governança

- **Cuidado com Public Synonym**: o namespace `PUBLIC` é global. Excesso gera conflito de nomes, ambiguidade na resolução e brecha de segurança.
- **`DROP SYNONYM` não apaga dado**: remove só a entrada do apontador. A tabela/view/sequence alvo continua intacta.
- **Auditoria de órfãos**: cruze `USER_SYNONYMS`/`ALL_SYNONYMS` com `ALL_OBJECTS` periodicamente para achar sinônimos cujo alvo sumiu.
- **Synonym não substitui grant**: privilégio é sempre no objeto base.
