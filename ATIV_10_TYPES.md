# 5SBD — Types (UDTs) no Oracle Database

O Oracle estende o modelo relacional com conceitos de orientação a objetos: é o paradigma **objeto-relacional (ORDBMS)**. Na prática, você define tipos próprios no catálogo (DDL) e usa esses tipos como coluna de tabela, como tabela inteira ou dentro de PL/SQL. Isso permite encapsular dado + comportamento (atributos + métodos), coisa que o modelo relacional puro não faz.

---

## 1. Fundamentos Teóricos

### Object Types

Um object type tem **especificação** (interface: atributos e assinaturas) e **corpo** (implementação dos métodos).

- `CREATE OR REPLACE TYPE ... AS OBJECT (...)` — especificação.
- `CREATE OR REPLACE TYPE BODY ...` — corpo com a lógica dos `MEMBER FUNCTION`/`PROCEDURE`.
- Persistência: pode virar o tipo de uma coluna (`endereco t_endereco`) ou dar origem a uma **object table** (`CREATE TABLE ... OF t_endereco`).

### Collection Types

| Tipo | Limite | Onde fica armazenado | Onde pode ser usado |
|---|---|---|---|
| **VARRAY** | Fixo (definido na criação) | Inline, na mesma linha da tabela | Schema (DDL) e PL/SQL |
| **Nested Table** | Sem limite superior | Out-of-line, em tabela auxiliar ligada por PK/FK oculta | Schema (DDL) e PL/SQL |
| **Associative Array** | Sem limite | Só memória, durante a sessão | Apenas PL/SQL (não existe em DDL) |

### Construtores e TABLE()

- Todo tipo ganha um **construtor implícito** com o nome do próprio tipo, na ordem dos atributos: `t_endereco('Av. Rio Branco','156',...)`.
- **`TABLE(coleção)`** transforma a coleção em um conjunto relacional (linhas), permitindo `JOIN`, `WHERE` e agregações normalmente. É o que faz nested table e VARRAY parecerem tabelas na consulta.

### MAP vs ORDER (comparação de objetos)

Para usar `ORDER BY`, `GROUP BY` ou `<`, `>`, `=` sobre um tipo complexo, o Oracle precisa de um método de ordenação.

| Método | Como funciona | Quando usar |
|---|---|---|
| **MAP** | Converte o objeto em um escalar (`NUMBER`, `VARCHAR2`, `DATE`); o Oracle compara os escalares | Ordenações frequentes e simples (mais eficiente, chamado uma vez por objeto) |
| **ORDER** | Recebe outro objeto do mesmo tipo e devolve -1, 0 ou 1 | Regra de comparação complexa, que não dá para reduzir a um escalar |

### Vantagens e desafios

**Vantagens**: reutilização semântica (tipo `Endereço`, `Telefone`, `Documento` usado em vários pontos) e integridade de domínio — a regra viaja junto com o tipo.

**Desafios**: indexar atributo aninhado exige índice de função/coluna virtual; ORMs de mercado (Hibernate, EF) têm suporte limitado a UDT nativo; DML massivo em coleções gera I/O extra na tabela auxiliar.

## 2. Roteiro Prático: Laboratório no Oracle APEX

### Etapa 1: Object type com atributos e métodos

```sql
CREATE OR REPLACE TYPE t_endereco AS OBJECT (
    logradouro  VARCHAR2(100),
    numero      VARCHAR2(10),
    bairro      VARCHAR2(50),
    cidade      VARCHAR2(50),
    uf          VARCHAR2(2),
    cep         VARCHAR2(9),
    MEMBER FUNCTION get_endereco_completo RETURN VARCHAR2
);
/

CREATE OR REPLACE TYPE BODY t_endereco AS
    MEMBER FUNCTION get_endereco_completo RETURN VARCHAR2 IS
    BEGIN
        RETURN logradouro || ', ' || numero || ' - ' || bairro || ', ' || cidade || '/' || uf || ' (CEP: ' || cep || ')';
    END;
END;
/
```

### Etapa 2: Coleções (VARRAY e Nested Table)

```sql
CREATE OR REPLACE TYPE t_telefones_varray AS VARRAY(3) OF VARCHAR2(20);
/

CREATE OR REPLACE TYPE t_dependente AS OBJECT (
    nome_dependente VARCHAR2(80),
    grau_parentesco VARCHAR2(30),
    data_nascimento DATE
);
/

CREATE OR REPLACE TYPE t_dependentes_nested AS TABLE OF t_dependente;
/
```

### Etapa 3: Tabela com colunas de tipos customizados

```sql
CREATE TABLE tb_clientes_corporativos (
    id_cliente      NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    razao_social    VARCHAR2(100) NOT NULL,
    endereco        t_endereco NOT NULL,
    telefones       t_telefones_varray,
    dependentes     t_dependentes_nested
) NESTED TABLE dependentes STORE AS tb_dependentes_store;
```

O `STORE AS` é obrigatório aqui: diz ao Oracle o nome da tabela auxiliar onde a nested table vai fisicamente morar.

### Etapa 4: Inserção com construtores

### Etapa 5: Consultas com métodos e `TABLE()`

```sql
-- atributos do objeto + método membro (alias da tabela é obrigatório)
SELECT c.id_cliente,
       c.razao_social,
       c.endereco.cidade AS cidade,
       c.endereco.uf AS estado,
       c.endereco.get_endereco_completo() AS endereco_formatado
FROM tb_clientes_corporativos c;

-- desaninhando a nested table
SELECT c.razao_social,
       d.nome_dependente,
       d.grau_parentesco,
       d.data_nascimento
FROM tb_clientes_corporativos c,
     TABLE(c.dependentes) d;

-- desaninhando o VARRAY
SELECT c.razao_social,
       t.COLUMN_VALUE AS numero_telefone
FROM tb_clientes_corporativos c,
     TABLE(c.telefones) t;
```

### Etapa 6: Dicionário de dados

```sql
SELECT type_name, typecode, attributes, methods
FROM user_types
ORDER BY type_name;

SELECT type_name, attr_name, attr_type_name, length
FROM user_type_attrs
ORDER BY type_name, attr_no;
```

## 3. Exercícios Práticos de Fixação

### Exercício 1: Métodos de um tipo

Criar `t_retangulo` com `largura` e `altura`, mais `calcular_area` e `calcular_perimetro`.

```sql
CREATE OR REPLACE TYPE t_retangulo AS OBJECT (
    largura NUMBER,
    altura  NUMBER,
    MEMBER FUNCTION calcular_area RETURN NUMBER,
    MEMBER FUNCTION calcular_perimetro RETURN NUMBER
);
/

CREATE OR REPLACE TYPE BODY t_retangulo AS
    MEMBER FUNCTION calcular_area RETURN NUMBER IS
    BEGIN
        RETURN largura * altura;
    END;

    MEMBER FUNCTION calcular_perimetro RETURN NUMBER IS
    BEGIN
        RETURN 2 * (largura + altura);
    END;
END;
/

-- teste sem precisar de tabela
SELECT t_retangulo(10, 5).calcular_area()      AS area,
       t_retangulo(10, 5).calcular_perimetro() AS perimetro
FROM dual;
```

Retorno esperado: área 50, perímetro 30.

### Exercício 2: MAP para ordenação

Adicionar um `MAP MEMBER FUNCTION` que devolva a área; o Oracle passa a conseguir comparar e ordenar objetos do tipo.

```sql
CREATE OR REPLACE TYPE t_retangulo AS OBJECT (
    largura NUMBER,
    altura  NUMBER,
    MEMBER FUNCTION calcular_area RETURN NUMBER,
    MEMBER FUNCTION calcular_perimetro RETURN NUMBER,
    MAP MEMBER FUNCTION ordenar RETURN NUMBER
);
/

CREATE OR REPLACE TYPE BODY t_retangulo AS
    MEMBER FUNCTION calcular_area RETURN NUMBER IS
    BEGIN
        RETURN largura * altura;
    END;

    MEMBER FUNCTION calcular_perimetro RETURN NUMBER IS
    BEGIN
        RETURN 2 * (largura + altura);
    END;

    MAP MEMBER FUNCTION ordenar RETURN NUMBER IS
    BEGIN
        RETURN largura * altura;   -- critério de ordenação: área
    END;
END;
/

CREATE TABLE tb_retangulos (
    id NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    r  t_retangulo
);

INSERT INTO tb_retangulos (r) VALUES (t_retangulo(3, 4));
INSERT INTO tb_retangulos (r) VALUES (t_retangulo(10, 2));
INSERT INTO tb_retangulos (r) VALUES (t_retangulo(5, 5));
COMMIT;

SELECT x.r.largura, x.r.altura, x.r.calcular_area() AS area
FROM tb_retangulos x
ORDER BY x.r;   -- funciona só por causa do MAP
```

Ordem esperada (área crescente): 3x4 (12), 10x2 (20), 5x5 (25). Sem o MAP, esse `ORDER BY` falha com `ORA-22950`.

### Exercício 3: Nested Table vs modelo relacional (1:N)

**Flexibilidade de consulta.** A nested table vence em simplicidade quando o acesso é sempre "pai com seus filhos": um `SELECT` com `TABLE()` resolve. Já o modelo relacional com duas tabelas exige `JOIN` e `GROUP BY` para remontar. Em compensação, quando a consulta precisa cortar por filho (ex.: "dependentes nascidos em 2015, de qualquer cliente"), o modelo relacional é mais direto: `WHERE data_nascimento = ...` na tabela filha, com índice próprio, sem `TABLE()`.

**Integridade referencial.** O modelo relacional é mais explícito e mais rico: FK com `ON DELETE CASCADE`, `UNIQUE`, `CHECK`, e o vínculo fica visível no dicionário. Na nested table a ligação é implícita (tabela auxiliar + PK oculta), o que é cômodo mas menos transparente para auditoria e mais confuso para quem só conhece SQL relacional.

**Ferramentas e ORM.** Aqui a relacional ganha fácil. Hibernate, Entity Framework e ferramentas de ETL tratam tabela + FK como cidadão de primeira classe. UDT e coleção nativa do Oracle costumam exigir mapeamento customizado ou nem ser suportados, o que encarece manutenção e integração.

**Performance em ETL.** Carga massiva por `INSERT ... SELECT` em tabelas relacionais é o caminho mais bem otimizado (direct-path load, paralelismo, partição). Com nested table, cada linha pai carrega a coleção e o Oracle precisa gravar na tabela auxiliar — mais I/O, mais complexidade e pior previsibilidade de plano. Regra prática: use coleção quando o dado é realmente um "anexo" do pai e pequeno; use duas tabelas quando o filho tem vida própria, volume alto ou precisa ser consultado sozinho.

## 4. Checklist de Boas Práticas

- **Alias obrigatório**: ao acessar atributo/método de UDT, use alias da tabela (`c.endereco.cidade`); `tb_clientes.endereco.cidade` dá erro de sintaxe.
- **Profundidade de aninhamento**: evite mais de dois níveis de tipos dentro de tipos — complica a query e atrapalha o CBO.
- **Dimensione o VARRAY**: só use VARRAY quando o limite é fixo e pequeno (meses, trimestres, telefones). Tamanho indefinido → nested table.
- **Dependências**: alterar um tipo base invalida tabelas e objetos dependentes. Antes de `DROP TYPE ... FORCE`, confira `USER_DEPENDENCIES`.
